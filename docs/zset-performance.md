# ZSet 新旧实现性能对比

测试日期：2026-10-18。以下结果是本机单线程测试的中位数，存在运行环境与随机跳表结构的波动，
不代表 Linux 上旧版的精确表现，也不能直接换算为有并发争用时的业务吞吐。

## 测试条件

- Windows/amd64，AMD Ryzen 7 5800H，Go 1.27.2，GCC 16.2.0。
- 旧实现取自提交 `97e703966220c7ef548bbb2dca641cefed1a26a0` 的 `pkg/go-zset`。
- 新实现为本次纯 Go 版本，`zset.go` 的 SHA-256 为
  `580A30C3E65D7800B363FA471519CBC348010732E9899A099392417CB7C65741`。
- 两版放在同一独立测试模块、同一测试二进制中，以相同接口调用；均使用 `CGO_ENABLED=1`、
  `-test.cpu=1`，关闭竞态检测。纯 Go 实现本身不调用 C。
- 每个规模、操作和实现分别运行五个独立进程，轮次交替先后顺序，取五次结果的中位数。
  独立进程也避免旧版的 C 内存泄漏在不同场景之间累计。
- 数据为 10,000 / 100,000 个成员，成员格式为 `member-%06d`（13 字节），初始分数为成员下标。
  预填充和初始 GC 位于计时区间之外。

### 旧版的 Windows 兼容调整

原 C 文件使用 Windows 不支持的 POSIX `random()`。测试副本仅替换这一调用：

```c
((unsigned long long)rand() * 65536ULL / ((unsigned long long)RAND_MAX + 1ULL))
```

保留原来的 `& 0xffff`、阈值和 1/4 层数提升概率，其余 Go/C 实现保持不变。
这改变了随机序列及随机数生成器，因此本报告比较的是 Windows 兼容基线。
Windows C 分配器也与 Linux 不同，倍数不宜推广到其他平台。

### 操作与次数

每轮排名、更新、范围查询及插入后删除各运行 100,000 次；查分和计数各运行 1,000,000 次；
批量裁剪运行 200 次。两版始终使用相同的次数与数据公式。

- 成员访问下标：`(i * 7919) % size`，分散访问整个集合。
- 更新分数：`float64(((i + 1) * 7919) % 1000003)`，覆盖已有成员的位置变化。
- 排名范围：起点分布于整个集合，每次返回 20 项；分数范围同样返回 20 项，包含两端。
- 插入后删除：添加同一个临时成员，再删除，以保持集合规模。
- 裁剪：每次调用 `Limit(size - 1000)`，删除末尾 1,000 项；恢复被删成员不计入耗时和分配。
- 结果写入包级变量，保持集合存活至测量结束。两版的基本行为对照测试通过。

此前 README 的单版基准采用顺序访问、固定范围与不同更新公式；不能将该数值直接与此表拼接比较。

## 耗时

单位均为 ns/op。`旧/新` 大于 1 表示纯 Go 版更快，小于 1 表示更慢。

| 10,000 个成员 | 旧 CGo | 纯 Go | 旧/新 |
| --- | ---: | ---: | ---: |
| Rank | 907.9 | 322.8 | 2.81 |
| RevRank | 712.2 | 297.5 | 2.39 |
| 更新已有成员分数 | 1,388 | 640.4 | 2.17 |
| Range 返回 20 项 | 2,126 | 538.5 | 3.95 |
| RangeByScore 返回 20 项 | 2,670 | 1,226 | 2.18 |
| Score | 32.27 | 32.01 | 1.01 |
| Count | 3.073 | 7.042 | 0.44 |
| 插入后删除一项 | 1,146 | 668.5 | 1.71 |
| Limit 删除 1,000 项 | 518,806 | 69,103 | 7.51 |

| 100,000 个成员 | 旧 CGo | 纯 Go | 旧/新 |
| --- | ---: | ---: | ---: |
| Rank | 1,527 | 1,082 | 1.41 |
| RevRank | 1,627 | 1,076 | 1.51 |
| 更新已有成员分数 | 3,160 | 2,345 | 1.35 |
| Range 返回 20 项 | 5,556 | 1,186 | 4.68 |
| RangeByScore 返回 20 项 | 6,274 | 2,011 | 3.12 |
| Score | 54.06 | 61.18 | 0.88 |
| Count | 6.351 | 9.865 | 0.64 |
| 插入后删除一项 | 1,701 | 1,353 | 1.26 |
| Limit 删除 1,000 项 | 529,662 | 87,912 | 6.02 |

Count 新增读锁，单次开销增加约 3.5–4 ns，修复了旧实现并发读写计数时的数据竞争。
Score 两版均为读锁加 Map 查询；10 万成员样本中新版约慢 13%，但该场景运行波动较大，
不应据此认定存在稳定的 13% 回退。

排名、更新的优势随数据规模扩大而缩小，范围和裁剪仍有明显提升。
本次样本存在离群值，例如 10 万成员更新的旧版范围为 2,637–4,483 ns、新版为 2,130–5,599 ns。
表中倍数是中位数之比，未进行统计显著性检验，应作为本机参考值。

## 分配与内存

以下是 Go 基准统计的堆分配，两种规模的分配结果一致：

| 操作 | 旧版 B/op | 新版 B/op | 旧版 allocs/op | 新版 allocs/op |
| --- | ---: | ---: | ---: | ---: |
| Rank / RevRank / 更新分数 | 0 | 0 | 0 | 0 |
| Range 返回 20 项 | 640 | 320 | 21 | 1 |
| RangeByScore 返回 20 项 | 1,328 | 1,008 | 26 | 6 |
| 插入后删除一项 | 0 | 85 | 0 | 2 |
| Limit 删除 1,000 项 | 32,384 | 0 | 1,001 | 0 |

**Go 的 B/op 和 allocs/op 不包含 C 分配。** 因此旧版插入、排名和更新显示的零分配，
不能理解为总内存零分配，也不能据此判断旧版插入比新版省内存。

旧版 `newslobj` 先分配 `C.CString`，再在 `slCreateObj` 中复制到另一份 C 内存：
最初的 CString 没有释放；Rank/Rem 等操作使用的临时 slobj 及其字符串也没有释放。
纯 Go 版没有这些临时 C 对象，已有成员更新还会复用节点与层数组。

### 独立进程的内存增长实验

另行在独立进程中预填充 10,000 个成员、预热 10,000 次排名查询，执行 GC 后记录 Windows
`GetProcessMemoryInfo` 的 `PrivateUsage`，再执行 1,000,000 次指定操作，GC 后再次记录。
集合在整个测量期间保持存活。此处包含 C 内存，测量没有用于上面的耗时结果。

| 重复操作 | 旧版私有字节增量 | 新版私有字节增量 |
| --- | ---: | ---: |
| 1,000,000 次 Rank | 103,337,984（约 98.6 MiB） | 360,448（约 0.34 MiB） |
| 1,000,000 次已有成员更新 | 150,130,688（约 143.2 MiB） | 360,448（约 0.34 MiB） |

这是各场景单次进程级内存增量实验，包含运行时、分配器与碎片的影响，
不能视为严格的每操作分配量或集合的稳态大小。结果与源码中的 C 临时对象泄漏相符。
新旧集合的总驻留内存、纯 Go 节点对 GC 扫描的影响及长期并发业务负载尚未单独测量。

## 结果解释与本地材料

- 原版排名需要构造 C 查询对象并跨越 Go/C 边界；新版直接在 Go 跳表查询。
- 原版范围查询对每个成员执行 C 遍历调用和字符串复制；新版直接收集已有字符串。
- 原版裁剪先查询再逐项删除，预期 O(K log N)，并反复加锁；新版单次写锁下执行
  O(log N + K) 的连续删除，不构造成员列表。
